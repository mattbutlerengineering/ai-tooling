## What it does

A coding-agent skill that runs a six-phase security audit: reconnaissance (architecture,
trust boundaries, a `coverage-ledger.json`), coverage-led hunting by isolated hunter agents,
adversarial candidate validation by a *fresh* agent that tries to disprove each candidate,
structured output into `findings.json`, independent record verification, and target-neutral
reporting. It is the skill Cloudflare says seeded its internal vulnerability-discovery
harness.

The part that distinguishes it from every other security skill in this catalog is that two
of the six phases are **not prompts**. `validate-findings.cjs` and
`validate-coverage-ledger.cjs` are zero-dependency Node validators the parent agent is
instructed to run after creating the ledger, in Phase 4, and again after every Phase 5
replacement. They interpret `report-schema.json` directly and exit non-zero on a malformed
record — so the agent's output is gated by a deterministic check rather than by another
model's opinion.

The schema encodes the methodology rather than merely typing it. Three verdicts are
structurally different objects: `confirmed` requires `trace`, `evidence`, `execution`
(with `observed_result`), `remediation`, `severity` and `confidence`; `needs_validation`
requires `blockers` and a `validation_plan` and has **no `severity` property at all**;
`rejected` requires the disproving `reason`. "An unvalidated lead carries no severity" is
therefore a parser rule, not a guideline.

## How we tested it

**Evidence:** RUN

Cloned at `HEAD` (pushed 2026-09-14) and exercised the deterministic half hands-on with
Node v22.22.3. Two things were run: the shipped test suites, and a set of hand-built
adversarial fixtures aimed at the skill's central claim.

**Shipped suites — 65/65 pass, no dependencies, no network:**

```
$ node validate-findings.test.cjs        # 1..34  — pass 34, fail 0 (897ms)
$ node validate-coverage-ledger.test.cjs # 1..31  — pass 31, fail 0 (755ms)
```

**Adversarial fixtures.** Six `findings.json` files written by hand against
`report-schema.json`, run through `validate-findings.cjs`:

| Fixture | What it is | exit | Result |
|---|---|---|---|
| `A-valid` | complete `confirmed` record | 0 | `PASS: 1 findings valid` |
| `E-nv-clean` | complete `needs_validation` record | 0 | `PASS: 1 findings valid` |
| `B-notrace` | `confirmed` with `trace: []` | 1 | `trace: must have at least 1 item(s), got 0` |
| `C-nv-severity` | `needs_validation` + severity, other fields loose | 1 | 8 errors incl. the severity rule |
| `F-nv-severity-only` | `E-nv-clean` **plus one field**: `severity` | 1 | `needs_validation finding must not contain "severity"` |
| `D-fabricated` | schema-perfect `confirmed`, every cited file invented | **0** | `PASS: 1 findings valid` |

`F` is the controlled one: it is byte-identical to the passing `E-nv-clean` except for the
added `severity` object, and it flips PASS→FAIL with a bespoke, non-schema error message.
The README's claim that an unvalidated lead cannot carry a severity is enforced, and the
enforcement is reachable by a one-field delta.

`D` is the informative failure. It cites `does/not/exist.js:9999` and `also/fake.js:4242`
in a repo where neither path exists, with an invented excerpt, and the validator reports
`PASS: 1 findings valid`. Confirmed by reading `validate-findings.cjs`: it never touches
the filesystem — no `fs` read of a cited `file`, no line-count check.

I did **not** run the full six-phase audit against a real target. That needs a
multi-agent run under an OS-enforced sandbox with external networking disabled, which is a
materially different (and expensive) exercise; Phases 1–3 and 5–6 here are assessed
source-grounded, from `SKILL.md`, `HUNTING.md` and `VALIDATION-AND-REPORTING.md`, not run.
The vendor's "a single run found roughly half of the vulnerabilities that repeated runs
found in total" is **Cloudflare's figure, not ours** — we measured nothing about detection
rate.

## Test design

- **Task/corpus:** the repo's own two test suites at `HEAD`, plus 6 hand-built
  `findings.json` fixtures (1 valid `confirmed`, 1 valid `needs_validation`, 3 malformed,
  1 schema-valid-but-fabricated) generated by a committed script.
- **Baseline:** for the severity rule, the with/without arm is `E-nv-clean` vs
  `F-nv-severity-only` — the same record ± one field.
- **Metric:** validator exit code and emitted error text (a mechanical oracle).
- **Reproduce:**
  ```
  git clone --depth 1 https://github.com/cloudflare/security-audit-skill
  cd security-audit-skill/skills/security-audit
  node validate-findings.test.cjs && node validate-coverage-ledger.test.cjs
  node validate-findings.cjs <fixture>.json; echo "exit=$?"
  ```

### Test design — skills

- **Triggering:** **not measured.** The `description` is unusually explicit about mode —
  it separates guidance mode from the full workflow and names the phrases that escalate
  ("audit", "pen test", "full/comprehensive/end-to-end", "report artifacts"), and `SKILL.md`
  instructs the agent to ask one focused question when the request is ambiguous. That is a
  well-designed trigger surface on inspection; no should-fire/shouldn't-fire prompt set was
  run against it.
- **Output A/B:** **not measured** for the agent half — no with-skill-vs-baseline audit run.
  The A/B above is on the deterministic validator, not on agent behaviour.
- **Not run?** The six-phase audit was not run. The validators were.

## What worked

- **The deterministic gate is real and strict.** My first hand-written "valid" fixture was
  rejected with 8 precise errors because I had guessed the `evidence`/`conditions`/`execution`
  sub-shapes. A validator that catches a careful human's guesses will catch an agent's.
- **The methodology is encoded in the schema, not just described.** `needs_validation`
  having no `severity` property plus `additionalProperties: false`, and a bespoke rule
  emitting `needs_validation finding must not contain "severity"`, is the "severity requires
  impact" principle made mechanical.
- **Zero dependencies, offline, fast.** 65 tests in ~1.6s total with nothing installed;
  the validators are plain `.cjs` reading a JSON schema they interpret themselves. This is
  the same gate-it-in-CI shape this repo uses for its own detectors.
- **Adversarial validation by construction.** "The agent that checks a finding is never the
  agent that found it" is a structural rule, and Phase 5 sends *material replacements* back
  to another independent verifier — the loop is closed rather than one-shot.
- **MIT, first-party, current.** ★16.7K, pushed 5 days before this eval, from a vendor with
  a published account of running it at fleet scale.
- **Re-runs are additive**, using prior ledgers to target gaps and revalidate changed source
  rather than treating stale work as covered.

## What didn't work or surprised us

- **The validator checks shape, never truth.** `D-fabricated` passes: a schema-perfect
  finding citing files that do not exist is `PASS: 1 findings valid`. The validator never
  opens a cited file. This is a division of labour, not a bug — truth is Phase 5's job, and
  Phase 5 is agents — but it means the machine-checkable guarantee is "well-formed and
  internally consistent", and **not** "verified". Anyone reading `findings.json` as
  independently verified because it passed the validator is reading more than the exit code
  says.
- **Cost is unstated and structurally high.** Isolated hunters per ledger unit, coverage
  critics, a fresh verifier per unique candidate, and independent record verifiers in
  Phase 5 — the design multiplies agents deliberately. There is no token or wall-clock
  figure anywhere in the repo, and none was measured here.
- **The sandbox requirement is a real precondition, not a footnote.** Without an
  OS-enforced sandbox (no external network, sanitized env, resource limits, scratch-only
  writes) the workflow is documented to keep leads at `needs_validation` instead of
  executing target code — so an unsandboxed run yields a thinner report by design.
- **13 markdown files, ~2,100 lines of instruction.** Attack-class files are loaded per
  target type, but this is a large surface to keep in an agent's working context, and
  nothing in the repo measures the context cost.
- **Vendor's own detection figure is unreproduced.** "A single run found roughly half"
  implies you should budget for repeated runs to get the stated value, which compounds the
  cost point above.

## Quality signals affected

| Signal | Impact | Evidence |
|--------|--------|----------|
| Correctness | + | Adversarial validation plus a schema gate that rejected 3 of 3 malformed records and caught my own guessed sub-shapes. |
| Speed | − | Six phases with fan-out hunters and per-candidate verifiers is slower than a single-pass review; no figure published or measured. |
| Maintainability | neutral | Produces a report and a `findings.json`; it does not change the audited codebase. |
| Safety | + | The whole point — whole-repo vulnerability discovery with a bounded, source-traced output contract, MIT-licensed so it can be vendored. |
| Cost Efficiency | − | Agent fan-out is the design; vendor implies repeated runs are needed for full value, and no cost figure exists. |
| Verifiability | + | The strongest signal here: `findings.json` is machine-checkable against a published schema, verdicts are structurally distinct, and `needs_validation` cannot borrow a severity. Tempered by `D-fabricated` — the gate proves shape, not that a cited line exists. |

## Verdict

**CONDITIONAL** — `adopt-if:` you need a deep, whole-repo security audit (pre-release, a
security-sensitive service, pre-external-audit) **and** can provide an OS-enforced sandbox
and absorb a multi-agent run. It is the best-licensed answer in this catalog to the job
[`trailofbits/skills`](https://github.com/trailofbits/skills) was SKIPped for: that eval
rejected the methodology pack on CC-BY-SA-4.0 ShareAlike attaching to any repo that vendors
the skill text, and this is MIT, first-party, ★16.7K and currently maintained — the same
job without the license contamination.

It does **not** replace [`security-guidance`](https://github.com/anthropics/claude-plugins-official/tree/main/plugins/security-guidance)
(STACK, ADOPT, MEASURED), which reviews the diff in the loop. These are different jobs at
different cadences: one runs on every change, this one runs when you sit down to audit.

Held at CONDITIONAL rather than ADOPT deliberately. The verdict is entitled — the tool was
exercised (`RUN`) and the condition above is genuine — but the run covered the deterministic
half only. Promotion to ADOPT/MEASURED needs a full six-phase audit against a target with
known findings, with token and wall-clock cost recorded; until then the unmeasured half is
the agent orchestration, which is most of the tool.
