# AI Tooling

Documentation-only repo. No build, test, or deploy commands.

## Purpose

An operating manual for AI-assisted development that produces high-quality code and keeps improving. Inventory and evaluation of AI tools, skills, agents, frameworks, harnesses, workflows, and MCP servers — organized around the dev loop stages where tools intervene and the quality signals they move.

Evaluates tools against six quality signals: Correctness, Speed, Maintainability, Safety, Cost Efficiency, and Verifiability (can a human confirm the output is right, at the rate it's produced — see ADR-0004). Evals written before Verifiability existed record five; it is required for new evals, not retrofitted. The workflow has three layers per stage (process, tooling, infrastructure) connected by feedback arcs that make each cycle better than the last.

## Structure

- `PLAYBOOK.md` — the one-page front door: what to install / how to work / what to watch, routing to the depth docs (hand-maintained router, never a data mirror)
- `CATALOG.md` — flat inventory of 679 tools, organized by 13 categories with overlap markers
- `WORKFLOW.md` — dev loop stages (inner + outer), tools per stage, quality signals, adoption guide
- `STACK.md` — recommended stack (~25 tools to actually install, with commands)
- `STACK-LEDGER.md` — machine-readable record of why each ADOPT/KEEP tool is/isn't in STACK (data foundation for the #70 drift gate)
- `evaluations/` — hands-on tool evaluations following `TEMPLATE.md`
- `methodologies/` — external AI-native SDLC methodologies mapped onto our dev loop + stack (synced to plugin; see ADR-0003)
- `discovery/` — historical bulk discovery logs (loops 1–21); new scans are GitHub issues labeled `scan` (see discovery/README.md)
- `skills/` — source skills for reference
- `plugin/` — installable Claude Code marketplace package (skills, docs, hooks)
- `README.md` — repo overview with install instructions

## Catalog format

Each entry is a row in a markdown table with these columns:

| Column | Description |
|--------|-------------|
| Name | Tool name, linked to repo |
| Type | tool / skill / plugin / framework / harness / platform / MCP server / reference |
| One-liner | Plain-language description, ~10-15 words |
| Problem it solves | The specific pain point, ~1 sentence |
| Overlaps with | Other catalog entries that address a similar problem (may also name a notable external tool or installed skill as a conceptual peer) |
| Ships inside | The `owner/repo` this artifact is a *component of*, when it is not independently installable — else empty (#343) |

**The `Ships inside` column (#343).** A row for a skill that ships inside a pack is
not an independent lead: installing the pack settles it, a redundancy verdict against
its own container is meaningless, and the queue overstates the work by one slot per
facet. The column makes that containment **explicit and machine-readable** instead of
leaving it to be re-derived (badly) from names — `triage.py` bands a declared row into
**P5 ships-inside**, ahead of even the mechanical bands, because a contained row's own
license and archival state answer a question about the *container's* artifact, not its
own. Detector X reports a fully-declared group as `DECLARED` rather than counting it.
Three rules:

- **The container is a slug, never a display name.** Same root as #366 and #374 — a
  basename is not a synonym. `mattpocock/skills`, not `skills`.
- **Empty is the default and means "independently installable".** Most rows are.
  Filling it wrongly *hides* a real lead, which is the expensive direction — so this
  is the one rule with a **falsifier**: detector AF asks whether the declared subpath
  publishes its own package, and three cells failed (#431). It only ever *refutes*;
  publishing nothing is not proof of containment.
- **The `## Catalog entry` mirror in `evaluations/` stays five columns.** Width is
  derived from each table's own header (`catalog_lib.validate_catalog_rows`), so the
  ~520 existing mirrors are valid as-is; bumping the constant would make every one of
  them a detector O finding. Copy the 6th cell into a mirror only if you also widen
  that mirror's header.

## Source of truth

- `plugin/docs/` is a synced copy — never edit directly
- `plugin/skills/` is authoritative for skills; `skills/` is derived (paths stripped)
- Run `./sync-plugin-docs.sh` after any root doc or plugin skill change
- `plugin/README.md` is **hand-authored and stays that way** — it is the plugin's front door (install, skills list, hooks, `${CLAUDE_PLUGIN_ROOT}` paths), not a copy of root `CLAUDE.md`, so `sync-plugin-docs.sh` has nothing to mirror. It was `plugin/CLAUDE.md` until #441, on a claim that was never true: `claude plugin validate` says outright that *"CLAUDE.md at the plugin root is not loaded as project context"* — Claude Code never loaded it, as project context or otherwise, so the file addressed an agent that could not read it while the plugin shipped without the `README.md` the plugin docs name as the documented home for install and usage. **The gates were right and the reasoning under them was a guess**, which is the part worth keeping: this page drifts silently — its eval count sat 87 behind (#302) and its quality-signal list stayed at five for the whole life of the sixth signal (#313) — and both of those are defects *for the human reading it on GitHub*, which is who reads it and always was. The rule is therefore **gate the shared facts, not the file** — every fact it restates from root must have a generator or a test (counts → `reconcile-counts.py`'s `EVAL_PATTERNS`/`TOTAL_PATTERNS`; quality signals → `TestPluginFrontDoorSignals`; the skills list → `check-plugin.py`'s `FRONT-DOOR` check). Restating a root fact here without one is the bug. A `CLAUDE.md` reappearing at the plugin root is that mistake returning and is itself a `FRONT-DOOR` finding — the plugin's way to ship *context* is a skill, and nothing here needs to reach a model: the five skills carry their own instructions, and a sixth whose only job is to describe the other five would be a token cost with no reader.

### Supported harnesses (Claude Code + opencode)

opencode is a supported harness alongside Claude Code. Both read this `CLAUDE.md`
(opencode reads it as its rules fallback — there is intentionally no `AGENTS.md`
content fork). Canonical homes per artifact, with the other harness derived/synced
(ADR-0002; never hand-maintain a duplicate that drifts):

- **Instructions** → `CLAUDE.md` (both harnesses)
- **Repo skills** → `.claude/skills/` + `.agents/skills/` (both harnesses auto-discover; `.claude/skills/find-skills` is a symlink to `.agents/skills/find-skills`)
- **Specialized agent (`eval-runner`)** → `.opencode/agents/` canonical; `.claude/agents/eval-runner.md` is a symlink to it (one source file, zero drift)
- **Hook logic** → opencode plugins in `.opencode/plugins/` (`commit-gate.ts`, `auto-sync.ts`) that call the **same** `audit-evals.py --offline` / `sync-plugin-docs.sh` scripts Claude Code's hooks use — so the local opencode, local Claude Code, and CI (`make check`) gates reference one implementation
- **Deterministic gates** → custom commands `/check` `/fix` `/sync` (opencode) and `make check`/`make fix`/`./sync-plugin-docs.sh` directly

**Lockstep invariant:** any change to a hook behavior must keep the opencode
plugins, the Claude Code `.claude/hooks/` scripts, and `.github/workflows/integrity.yml`
in lockstep — they all gate against the same coupled scripts, so they must not drift.
The **shipped** plugin hook (`plugin/hooks/validate-counts.sh`) is held to the same rule
since #443, and it is the one that had escaped it: it re-implemented the count extraction
in bash, grepping for the *prose phrasing* each number sits in (`inventory of N`,
`N evidence-based evaluations`) while `reconcile-counts.py` owned the canonical patterns
for the same numbers. Two extractors for one fact, in two languages, coupled by nothing —
so a prose rewrite failed the Python loudly and made the bash silently stop matching, and
**3 of its 5 checks had rotted to no-ops**, two of them within three days (#436 rewrote
README's eval line; #442 renamed `plugin/CLAUDE.md`). It delegates to
`reconcile-counts.py --check` and `sync-plugin-docs.sh --check` now, which also picks up
patterns the bash never knew existed — `COMPOSITION_PATTERNS` landed in #435 and no hook
was taught it. What let this run for so long is the **test direction**: the hook's only
test asserted it is *silent on a clean tree*, which is the symptom — a hook with zero live
checks is maximally silent, so the test passed more easily the more broken the hook got.
`TestValidateCountsHook` now pins both directions, and pins that the hook does not
re-extract a count from prose.

The **commit** gate is the same rule one file over, and it had escaped it for a different
reason: it never re-implemented anything, it simply **stopped keeping up**. Both halves
ran `python3 audit-evals.py --offline` — **1 of the 13** offline gates `make check`
enforces — while both described themselves in their own headers as running *"the offline
subset of `make check`"* (#459). Every gate added since #153 widened the hole in silence,
because nothing coupled the hooks' list to the Makefile's: on a tree with a stale
`NEXT-EVALS.md`, a desynced `plugin/docs/`, a missing `**Stars:**` line, a dead relative
link or a stale `WATCHLIST.md`, the commit gate passed and CI failed. Both now call
**`make check-data`**, the one definition of that set — `check-offline` minus the two
linters and the unit suite — and `check`/`check-offline` delegate to it too, so a gate
added there reaches the Makefile, CI and both hooks at once. The two exclusions are
stated and measured rather than incidental: ruff/mypy need the pinned dev venv and a
contributor without it must not be blocked from committing, and the unit suite is 15.9s
testing the *scripts* rather than the *tree*. Full coverage costs ~3.5s per commit
(median 4.0s against 0.55s). One thing the delegation made reachable and both files got
wrong beforehand: **"could not run" is not "failed"** — each promised to fail open if the
audit itself could not run, and each blocked on any non-zero exit, so a missing binary
would have blocked every commit. `make` cannot signal that difference through its exit
code (it exits non-zero for an absent target and for a real finding alike), so the three
preconditions are probed *before* the run and never inferred from it. `TestIntegrityMakefile`
pins the target's contents in both directions and pins that both hooks call it rather than
keeping a private list, reading each hook's **code** and not its comments — a header
narrating the gate it used to run is not a header re-running it (#451's rule).

## Integrity audit

- **`make check` is the canonical gate; `make fix` is the canonical repair.** `make check` runs the full gating set in `--check`/verify mode — exactly what `.github/workflows/integrity.yml` enforces (the lint gates `ruff`/`mypy`, offline detectors B/D/G/J/K/O, `--selftest`, the `test_automation` unit suite, `reconcile`/`backfill`/`check-stars`/`verify-installs`/`tier-stack`/`sync-plugin-docs` `--check`, and the network install resolver A) — and exits non-zero on the first failure. `make fix` runs the apply-mode fixers in dependency order (`ruff --fix` → `reconcile-counts` → `backfill-evidence` → `backfill-lastverified` → `tier-stack` → `triage` → `watchlist` → `sync-plugin-docs`) then re-runs `check`, so a clean exit means the tree is green. **Both halves are pinned, and the repair half was pinned in no direction until #461** — deleting `backfill-evidence`, `triage` and `watchlist` from the recipe left all 581 tests green, because every assertion about `fix:` was positional (ruff first, `check` last) or negative (the two local-only fixers stay out). `TestIntegrityMakefile` now derives the pin from the Makefile rather than hand-listing it: every `--check` line in `check-data` must either run in apply mode in `fix` or sit in a declared `NO_APPLY_MODE` set **with its reason** — so adding a gate forces an explicit decision instead of landing in neither. That set replaces an *ordinal* the prose used to state in three places ("the only", "the second", "the second"), three different answers for a set of four, with nothing that could check any of them; the chain above is itself compared to the recipe, here and in the opencode `/fix` template, both of which named four of its eight steps. CI's `audit` job calls `make check`, so the local and CI gate sets can't drift (pinned by `test_automation.py`'s `TestIntegrityMakefile`). The thirteen offline `--check` gates live once, in **`make check-data`**, which `check`, `check-offline` and both commit hooks all delegate to (#459) — add a gate there and it reaches every one of them. The individual scripts below are still runnable directly when you want one gate in isolation.
- `python3 audit-evals.py` runs the gating detectors (A install, B fabrication, D verdict sync, G comparison consistency, J stack-derivation drift, K verdict evidence, O row shape) and exits non-zero on any problem (gate it in CI/pre-commit); opt-in detectors C/E/F/I and `--selftest` add more checks:
  - **install resolver** — every install command in `STACK.md`/`CATALOG.md`/`evaluations/` must point at a real artifact (npm/PyPI/crates.io/GitHub). A broken command means the tool was likely never run. The **only gating detector that touches the network**, which is why it now reports `n/total target(s) checked` and **three** outcomes rather than two (#447). Only a `404` is `BROKEN` and fails the build; a 429, a 5xx, a timeout, a missing `npm`/`gh` binary or a DNS blip is `UNCHECKED` — printed with its reason, counted, and **never** a build failure. That split is detector C's rule (#319) arriving four hundred lines late, and this detector had broken it in **both directions at once**. `http_ok` folded every non-200 into `False` under an inline comment reading *"any failure here means 'cannot verify', not 'broken'"* — the correct rule stated one line above the code that contradicted it — so a rate-limited crates.io failed the whole `make check` on `BROKEN [crates] abtop` while crates.io answered `200`, and **re-running the identical tree passed**: same commit, two verdicts, the definition of a non-deterministic gate and the exact thing `CLAUDE.md` forbids three times over (detectors R, V and AF each decline to gate because *"failing the build on one would fail it for a reason no commit caused"* — a rule written for the report-only detectors while the one that actually gates ignored it). In the other direction `_run_ok` returned `True` on a missing binary or a timeout, so **57 of 85** targets could report as resolved without being reached, and the headline `OK — all checked install targets resolve` was true and useless — #319's *"silence is not success"* inside the gate. A non-zero exit is **not** proof either: `npm view` and `gh api` exit non-zero for a registry 5xx and a rate limit as well as for a missing package, so classification keys on the 404 marker each prints (`E404` / `HTTP 404`) and every other failure is `UNCHECKED`. Two reporting rules: `BROKEN` findings are **per occurrence** (a dead package cited in three evals is three rows to fix) while `UNCHECKED` findings are **deduped by target and capped with the count disclosed**, because an unreachable registry is one thing to re-run rather than N rows to fix. `max_workers=24` stays — throttling lowers the *rate* of unknowns and never classified them. (`--installs` only)
  - **fabrication classifier** — each eval's "How we tested" must either disclose it was not run or show a verified hands-on run; a section asserting a specific run with no honesty disclaimer is flagged. (`--fabrication`/`--offline`, no network)
  - **verdict sync** — each eval's `## Verdict` must agree with its `COMPARISON.md` row (tolerates dual verdicts and the KEEP/installed status). (`--verdicts`, offline)
  - **comparison consistency** — `COMPARISON.md`'s per-stage summary must sum to its own body rows and its Total must equal the `CATALOG.md` entry count; catches manual count drift between the two authoritative files. (`--comparison`, offline, gating, on by default)
  - **stack-derivation drift** — `STACK.md` must be derivable from the verdict data + the `STACK-LEDGER.md` exclusion ledger (#64): every ADOPT/KEEP tool is in STACK or has a logged exclusion reason, ledger verdicts match `COMPARISON.md`, and nothing marked in-STACK is actually missing from `STACK.md`. Kills the hand-maintained drift prior audits kept finding (abtop/codeburn, serena, documentation-writer). Since #416 it also runs the **reverse** direction: a STACK pick whose `COMPARISON.md` verdict is `SKIP` is a finding. Every other check here runs ledger → STACK or verdict → STACK, and a SKIP never reaches the ledger because the ledger holds ADOPT/KEEP only — so the one direction nothing asked was whether the **install list** recommends a tool the catalog *eliminated*. It did: `trailofbits/skills` sat in the Review table **and in the five-line copy-paste Quick Start block** for ten months after a bulk license triage SKIPped it, and the operation the block tells you to run — `claude install-skill` — is precisely the one the verdict exists to prevent, since a skill is *vendored* into the consuming repo and CC-BY-SA ShareAlike attaches to yours. Not a stale row: STACK is the page whose whole purpose is to be executed. Resolution goes **URL slug → catalog row name → verdict** (detector P's rule) rather than through the row's link text, because display names vary — "GSD" links to `obra/superpowers` — and keying on text would pass every renamed pick silently. **A slug is not always an identity, though, and until #463 this gated on a coin flip when it wasn't.** Nine of the thirty picks link a slug several catalog rows claim, and the index was built with `by_slug.setdefault(...)`, so whichever row `CATALOG.md` listed **first** answered for all of them: five picks — `feature-dev`, `code-review`, `pr-review-toolkit`, `security-guidance`, `skill-creator`, whose own verdicts are `KEEP`/`KEEP`/`KEEP`/`ADOPT`/`ADOPT` — were checked against `frontend-design`, a row that is none of them, and their nine-row group holds all four verdict values including `commit-commands` at `SKIP`. So the check was **not running** on those five, and it was one row-order away from firing on the wrong tool: swapping the `frontend-design` and `commit-commands` rows past each other — a pure reorder, no cell changed — turns a green `make check` into **five gating failures**, each naming a `KEEP` tool for a `SKIP` belonging to neither. That is the coin flip detector U (#401), detector AG (#453) and `verify-installs.py` each refuse by name, sitting inside the detector that **gates**. `resolve_stack_pick` asks the candidate set strongest-first: an unshared slug settles it; inside a shared one, the pick's **own text exactly naming a candidate** wins first, because STACK links a component pick at the pack root (`[resolving-merge-conflicts](github.com/mattpocock/skills)`) so the link identifies the *container* while the text identifies the *pick* — and "is `mattpocock/skills` SKIPped" is not the question that was asked. Detector P's warning does not reach that step: the text is not naming a tool from scratch, only telling nine already-slug-matched siblings apart, which is `verify-installs.py`'s **exact catalog name first** rule. Then an exact **link** match on a candidate's own URL. Matching neither is a **gating finding** naming the candidates rather than a silent skip — the check cannot say which row it would be checking, and silence there is #319's *"silence is not success"* inside a gate; a pick with **no** catalog row stays silent, which is the different gap the rule below is about. All nine resolve to their own row today, and a fixture pins the property that was violated: **findings must not depend on catalog row order**. That resolver has since moved into `catalog_lib` as `link_index`/`resolve_link` (#465): three report-only detectors — V, Z and AE — were asking the same question of the same 30 rows and each answering it with its own first-row read, so the fix that landed here was one of four copies of the defect. One fact, one implementation, the rule #443 states for the count extractors. A pick whose repo has no catalog row resolves to no verdict and is **not** a finding: that is a different gap, and flagging it here would flag a healthy row (detector V's rule). Gating in the same PR that removed the row, the sequencing the ledger check (#64) used — agreeing with a SKIP is bookkeeping, not judgement, so there is nothing here for a human to weigh. `WORKFLOW.md` keeps its `trailofbits/skills` line, now disclosing the SKIP (#414/#415): the methodology is worth *reading*, and only vendoring it is disqualified — which is exactly why the two files must give different answers, and why detector P's invariant (every STACK pick appears in WORKFLOW) is deliberately one-directional.   - **verdict evidence** — a strong verdict can't rest on a README skim: an ADOPT/KEEP eval must be run-backed (`Evidence` `MEASURED` or `RUN`) **or** carry an explicit honesty disclaimer in its "How we tested" section; a `REVIEW`/`SOURCE-ONLY` ADOPT/KEEP with no disclaimer fails. The escape hatch is the same not-run disclaimer vocabulary the fabrication classifier (B) recognizes (the `HONEST` regex — "source-grounded", "not run hands-on", "did not install", etc.); widen that vocab if it false-flags an honest review. To clear the gate, either graduate the eval to MEASURED/RUN (#68) or add the disclaimer. (`--verdict-evidence`, offline, gating, on by default)

(`--rows`, offline, gating, on by default; #198)
  - **link rot** (opt-in `--links`, ~450 requests) — every `github.com/owner/repo` link in `CATALOG.md` must resolve to its canonical name; flags 404s (dead) and silent renames (moved). **Read the `n/total checked` count, not just the verdict**: only a 404 means "gone", and every other failure (429 rate limit, 5xx, timeout) is *could not check*, reported as `INCONCLUSIVE` and never as OK (#319). Unauthenticated HEAD bursts of this size are heavily rate-limited — a local run typically verifies only a few dozen of the ~600 links, while the scheduled CI sweep gets through. Findings are always real; **absence of findings is only a pass when the checked count equals the total.**

Link rot misses these (the link still resolves). Note whether each is already disclosed.

Broader than `--skills` (all skill/plugin evals, not just ADOPT) and structural rather than verdict-based. Conservative by design — an eval counts as compliant on any triggering/A/B vocabulary, so an honest measured eval is never false-flagged; widen the vocab if it does, don't tighten it into a gate. A tracked metric, not a gate (mirrors `--skills`); gating new skill evals is the natural follow-up once the count stabilizes.

Surfaces candidates for human review; not a gate. **The legend's "installed skill" case is now demonstrated rather than assumed** (#398): `CATALOG.md`'s own column legend says a token may name "a notable external tool **or installed skill**" — so *it's an installed skill* is the sanctioned reason a token doesn't resolve, and nothing checked it, which is the unchecked install assertion ADR-0006 removed from `KEEP` one file over. F now joins the same records detector Y reads (`~/.agents/.skill-lock.json`, `installed_plugins.json`, `~/.claude/skills/`) and splits the bucket: a token an install record answers to is an **installed-peer**, printed with the source slug and **never counted** (V's `acked`, W's `cleared`, X's `FACETED`, Y's `SHADOWED`), while everything else stays a candidate. **`(ext.)` was the same shape and is now verified rather than obeyed** (#403): F skipped any token carrying the marker, so a row could assert a tool was outside the catalog and never be contradicted once it was added — which is exactly what happened to `aider`. A marked-external token whose identity resolves is now a **STALE-EXT** finding and it is **counted**, because it is a defect in the row rather than a peer awaiting review. Keyed on `identity_keys`, **never** `alias_keys` (#374): an alias-keyed run "resolves" `MCP (ext.)` to `mdn/mcp` by slash-basename, and between two rows that each name a tool a basename is not a synonym. `aider-style` is the mirror case — a descriptor rather than a name, so no key resolves it and only a human can repoint it. Repointing is not cosmetic: a dangling token contributes no `overlap_pressure`, a `triage.py` input, so `aider` sat at `discovery-log` carrying three invisible citations. Two further disclosures F can already read are also printed and never counted, asked **strongest-record-first** because a declaration is a fact about the artifact while an install record is a fact about one laptop (ADR-0006's split): a **contained-peer**, where the token's *own parenthetical* names a catalogued row — the `Ships inside` idea (#343) done informally, in the one column that has no such column, and the container is printed rather than swallowed because a parenthetical is prose that says where a peer lives, not that it isn't also a gap — and a **repo-peer**, a skill this repo ships under `skills/`, which is the strongest record available and the only one readable in CI (`skills/evaluate-tool/` is a real conceptual peer of a skill-evaluation tool and can never be a catalog row). Two of the legend's own examples still behave differently, now for a better reason — `tdd` is demonstrated by an install record, `systematic-debugging` by the container its citing row already disclosed. **Local-only, like Y**: `--overlaps` is opt-in and report-only so it never runs in CI, and with no records readable F reports precisely as it did before — the headline states the record count, because **0 records means "this machine keeps none", never "nothing is installed"**. - `python3 refresh-metadata.py` refreshes `repo-metadata.json` (license, archived, stars, pushed_at) for every catalogued GitHub repo. **The only script that calls `gh`**, so `make check` stays offline and CI never depends on ~580 API calls — the same split as `audit-evals.py`'s offline gates vs its opt-in `--installs`/`--archived` passes. `--stale` fetches only slugs missing from the cache. `--maintenance` additionally reads each README's head for a discontinuation banner and flags a license that disappeared since the last snapshot, writing `discontinued` and `license_lost` per record for detector V (#351) — it **doubles** the call count, which is why it is opt-in rather than part of every refresh. A `404` license value records *unreachable* (renamed, deleted, or DMCA-blocked — see `vkhanhqui/figma-mcp-go`) and is deliberately distinct from `NONE`, which means the repo is live and GitHub found no `LICENSE` **file**. That last word is load-bearing and used to be missing: GitHub's licensee detector reads a root LICENSE file and nothing else, so a repo declaring MIT in its README or `package.json` records `NONE` exactly like a repo granting nothing — and P4 mechanical-skip disposes vendored leads on that value. **9 of 28 `NONE` records declared a license anyway**, and five carried a SKIP whose stated ground was the license (#372). So when the API reports no license, the refresher looks where a human would — a README `## License` section, then `package.json`/`pyproject.toml`/`Cargo.toml` — and records `license_declared: {spdx, where, phrase}` (plus `conflict` when the README and the manifest disagree, as `builderio/agent-native`'s MIT-vs-ISC does). It fires only on `NONE`, so it costs a few dozen extra calls in a ~600-repo run rather than doubling it, and it is re-derived every fetch rather than carried forward — a repo that later adds a real LICENSE file drops the field on its own. What it records is a **candidate, not a license**: a README line naming MIT without the license text or a copyright holder is a thinner record than a LICENSE file, and whether that clears the adoption bar is a human's call. What it is not is an *absence*, and only an absence can carry a mechanical SKIP. `triage.py`'s `effective_license()` is what reads it, and it resolves in **both** directions — a README declaring AGPL disqualifies a vendored artifact on exactly the reasoning a parsed AGPL does. A missing cache is not fatal: the structural bands go empty rather than the gate exploding. `--containment` asks each `Ships inside` subpath whether it publishes its own package manifest and writes `member_packages: {subpath: package-or-null}` onto the **container's existing record** for detector AF (#431) — the same additive shape `discontinued` and `license_declared` use, so no phantom slug enters a file whose other consumers iterate it as repos, and a container with no record of its own is skipped rather than invented (that is AA's `UNROWED`, not this one's). It costs ~1 call per *declared row* (21 today), not per repo. Unlike `discontinued`, it is **carried forward** on every other path: losing it would silently turn an AF `REFUTED` into an `unchecked` — a finding disappearing without being fixed, which is the worst thing a report-only detector can do.
- **A header field is a claim; a comment beside it is provenance** (#451). Every field is read from **comment-stripped** text (`catalog_lib.strip_html_comments`, shared by `audit-evals.py`, `check-stars.py` and `backfill-lastverified.py` so a fourth copy can't drift), while a **marker about** a field is read from the raw text. Detector AC settled this for `**License:**` in #417 — *"an HTML comment carries provenance about the value, not the claim"* — and nothing generalised it, so detector Q, which **gates**, read `**Last triaged:**` out of `TEMPLATE.md`'s own guidance comment (*"OPTIONAL next line: `**Last triaged:**` … its ABSENCE is meaningful"*) and failed every eval created the documented way: copy the template, fill it in, write an honest hands-on `ADOPT`, watch `make check` go red. The finding's own remedy was worse than the finding — `<!-- triaged: human -->` **exempts an eval from the verdict ceiling**, so the obvious fix hands a brand-new file an exemption it never earned, while `<!-- triaged: bulk -->` forbids the very verdict the author was entitled to. The split is why this can never be one flag on a whole detector: **Q's markers are themselves comments**, so Q strips for the *stamp* and does not strip for the `bulk`/`human` markers, and the same asymmetry protects `backfill-lastverified.py`'s `<!-- backfilled from last git edit -->` sitting after a real value. `**Last verified:**` had the mirror bug in the direction nobody would notice — a commented example date became the eval's real date, and since that value is the anchor for detector L, `--staleness` and `WATCHLIST.md`, a comment carrying a *recent* date would have made a genuinely stale eval report fresh. **Live blast radius was zero and only by luck**: the single file whose stamp lives solely in a comment is `TEMPLATE.md`, which `DetectorContext` excludes — so the one file that could have demonstrated the bug was the one file exempt from it, and every copy was not. Scoped to **fields**: `## Verdict` and `## How we tested` are sections, still read whole, because a detector reading prose is a different question from a detector reading a declared value.
- `**Last triaged:**` is an **optional** eval header field, written only when the triage lane actually examines a lead; its *absence* is meaningful, so it is **never backfilled** (unlike `**Last verified:**`, whose git-derived floor date is honest — a lead that was never triaged has no floor, and stamping one would assert a look that never happened). `triage.py` sinks stamped leads within their band so each pass surfaces genuinely un-examined ones and the queue converges instead of re-shuffling. **Every stamp must be attributed**: a bulk lane writes `<!-- triaged: bulk -->` beside the date and a human pass writes `<!-- triaged: human -->`, and detector Q fails an unattributed stamp. The marker is what makes eliminate-only mechanical rather than a promise — Q can only police a lane it can identify, so a bare date looks exactly like a lane that behaved (#327). The human marker exempts the eval from the verdict ceiling, because reaching a real verdict is precisely what a human pass is for.

Four sections, each computed (not hand-maintained) from data already in the repo: (1) **Deferred** — every `DEFER` **verdict** in the repo with the re-evaluate trigger pulled from its eval's `## Verdict` (per TEMPLATE.md's DEFER definition; a missing trigger is itself an action item). ## Adding entries

- Use the `/add-catalog-entry` skill (`.claude/skills/add-catalog-entry/`) — it runs the full 8-file workflow (resolve slug, dedup, insert CATALOG + COMPARISON rows, propagate counts, sync, audit).

It also derives the **eval composition** — how many of the `evaluations/` files carry a real verdict, how many are still `discovery-log` leads, and how many are stubs or comparison documents — and gates those three numbers on the front page beside the total (#435). The reason is that the count was gated and its *label* was not: README called all 682 files "evidence-based evaluations with verdicts (ADOPT/CONDITIONAL/SKIP)", so `reconcile-counts.py` faithfully kept a correct number attached to a claim that was false for 389 of them — 258 headline `discovery-log`, the word #324 introduced across 324 files **precisely so a lead stops announcing a verdict it is not entitled to**, and restating them as verdicts in aggregate is that same defect one file up. ## Evaluations

- **Hands-on evaluations** use `evaluations/TEMPLATE.md` — copy it and fill every section with evidence from actual usage. The "How we tested it" section is mandatory; README-only evaluations are discovery logs, not evaluations.
- **Discovery logs** (`discovery/new-tools-loopN.md`) are the historical bulk-triage record — one-liner verdicts from scanning repos. They feed the catalog but don't constitute a full evaluation. New scans are GitHub issues labeled `scan` (see discovery/README.md), not new loop files.
- Use inner/outer loop vocabulary (Plan, Implement, Verify, Review, Ship, Reflect), not ACMM levels.
